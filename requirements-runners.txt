# ── SE O `pip install` FALHAR COM "SSL: UNEXPECTED_EOF_WHILE_READING" ──────────────────
# NÃO é a sua rede, e não é o pacote. `files.pythonhosted.org` resolve para QUATRO endereços
# IPv6 antes do IPv4; esta máquina tenta IPv6 primeiro e o caminho IPv6 está quebrado, então
# o handshake TLS morre. `pypi.org` responde 200 (é IPv4), o que faz o erro parecer aleatório
# — e pacotes já em cache "funcionam", o que engana ainda mais.
#
# Diagnóstico em uma linha (200 = o IPv4 está bom; o problema é a preferência IPv6):
#     curl -sS -o /dev/null -w "%{http_code}\n" --resolve files.pythonhosted.org:443:151.101.248.223 https://files.pythonhosted.org/
#
# CORREÇÃO PERMANENTE (PowerShell **como Administrador**) — faz o Windows preferir IPv4
# quando o IPv6 não tem rota. Conserta pip, curl, e tudo mais na máquina:
#     netsh interface ipv6 set prefixpolicy ::ffff:0:0/96 60 4
#
# CONTORNO SEM ADMIN (foi o usado em 15/07/2026): baixar os wheels por IPv4 e instalar
# offline. `curl -4` mostrou-se INSTÁVEL aqui (o DNS devolve IPv4 que ora funciona ora não);
# o que funciona é fixar o IP com `--resolve`:
#     curl -sS --resolve files.pythonhosted.org:443:151.101.248.223 -O <url-do-wheel>
#     python -m pip install --no-index --find-links=.wheels_ipv4 <pacote>
# As URLs saem da API do pypi.org (que responde): https://pypi.org/pypi/<pacote>/json
